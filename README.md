# anonchat

Anonchat is a test project for vibe coding. I wanted to create a useful application completely generated by AI. For this particular purpose I chose a field that I myself am not skilled in so that I can't be tempted to add any code to the project myself. So this is a kind of a proof-of-concept project.

In PROMPTS.md there's a collection of the prompts, used to generate the application. 

# ANONCHAT Local Development

## Prerequisites

- Docker
- Docker Compose (plugin `docker compose`)

## Start Local Stack

Start the backend and frontend development server together from the project root:

```bash
./start.sh
```

The script builds and starts the Docker Compose backend, then starts Vite on
all network interfaces at port `1420`. Open `http://127.0.0.1:1420/` on the
host, or `http://<host-lan-ip>:1420/` from another device on the same LAN.
Vite prints the available network URLs when it starts. Press Ctrl+C to stop the
frontend; stop backend containers separately with `docker compose down`.

If the host firewall blocks inbound connections, allow port `1420` only from
your LAN subnet. For a host on `192.168.0.0/24` using UFW:

```bash
sudo ufw allow from 192.168.0.0/24 to any port 1420 proto tcp
```

Do not expose the Vite development server to the public internet. If LAN access
still times out after allowing the port, check that the client is not on a guest
Wi-Fi network with device isolation enabled.

To start only the backend:

```bash
docker compose up -d --build
```

This starts:
- `redis-ram` (in-memory only)
- `chat-router`
- `proxy-guard`
- `proxy-middle`
- `proxy-exit`

## Run Proxy Manually (Without Compose)

You can run each proxy role directly with environment variables.

Notes:
- If `TLS_CERT_FILE` and `TLS_KEY_FILE` are not set, the proxy generates an ephemeral in-memory certificate.
- `NEXT_HOP_ADDR` is required for `guard` and `middle` when running outside the compose network.

Start exit node:

```bash
cd server/proxy
NODE_ROLE=exit LISTEN_PORT=9003 go run .
```

Start middle node:

```bash
cd server/proxy
NODE_ROLE=middle LISTEN_PORT=9002 NEXT_HOP_ADDR=127.0.0.1:9003 TLS_INSECURE_SKIP_VERIFY=true go run .
```

Start guard node:

```bash
cd server/proxy
NODE_ROLE=guard LISTEN_PORT=9001 NEXT_HOP_ADDR=127.0.0.1:9002 TLS_INSECURE_SKIP_VERIFY=true go run .
```

Optional explicit TLS certificate pair for a node:

```bash
TLS_CERT_FILE=/path/to/node.crt TLS_KEY_FILE=/path/to/node.key NODE_ROLE=exit LISTEN_PORT=9003 go run .
```

## Chat Router WebSocket Format

WebSocket endpoint:

```text
ws://127.0.0.1:8080/ws?user_id=<your_user_id>
```

Client -> server message:

```json
{
	"id": "msg-001",
	"to": "bob",
	"body": "hello"
}
```

Server -> client message:

```json
{
	"type": "message",
	"payload": {
		"id": "msg-001",
		"from": "alice",
		"to": "bob",
		"body": "hello",
		"sent_at": 1752400000
	}
}
```

Initial session ack from server:

```json
{
	"type": "session",
	"payload": {
		"user_id": "alice"
	}
}
```

## Quick Test Scenario (Online + Offline)

1. Start stack:

```bash
docker compose up -d --build
```

2. Open client A as alice:

```bash
npx wscat -c "ws://127.0.0.1:8080/ws?user_id=alice"
```

3. Open client B as bob:

```bash
npx wscat -c "ws://127.0.0.1:8080/ws?user_id=bob"
```

4. In alice, send message to bob (online path):

```json
{"id":"m1","to":"bob","body":"online delivery"}
```

5. Close bob, then in alice send second message (offline path):

```json
{"id":"m2","to":"bob","body":"offline delivery"}
```

6. Reconnect bob with same user_id; stored message is delivered and removed from Redis:

```bash
npx wscat -c "ws://127.0.0.1:8080/ws?user_id=bob"
```

7. Optional Redis check for offline keys:

```bash
docker compose exec redis-ram redis-cli KEYS "offline:*"
```

## Active Proxy Registry and Onion Packet Flow

The router exposes `GET /api/proxies/active`. It reads the active registry from
the `ACTIVE_PROXIES` environment variable and returns the JSON array consumed by
the Rust security core:

```json
[
  {
    "id": "guard-de",
    "address": "guard.example:9001",
    "country_code": "DE",
    "public_key_b64": "<32-byte X25519 public key in base64>",
    "latitude": 52.52,
    "longitude": 13.405
  }
]
```

The registry must contain nodes from at least three different countries. The
Rust entrypoint
`security_core::fetch_and_encrypt_chain(server_url, message)` fetches this
endpoint over HTTPS, selects Guard/Middle/Exit using `OsRng`, pads the message
with random noise, and returns a three-layer packet of exactly 4096 bytes.
Messages larger than 3912 bytes are rejected.

The Tauri bridge exposes `build_onion_packet_from_registry`, which invokes the
same Rust flow for the application transport layer and returns the packet as a
byte array. It reports fetch, selection, key, and encryption errors to the
caller instead of returning a success-shaped fallback. On successful selection,
the command publishes the selected Guard/Middle/Exit nodes (including country,
address and coordinates) to the `proxy-layer-changed` event bus and publishes a
structured status or error entry to `core-log`; the registered
`start_proxy_event_stream` command forwards both buses to the frontend with
Tauri `emit`.

For local or deployment configuration, set `ACTIVE_PROXIES` on `chat-router`
to a JSON array containing the currently active nodes. The router does not
persist this data; Redis remains memory-only and is used only for the short-lived
offline message queue.

## Rust Device Key Bootstrap Module

Location:
- client/security-core/src/device_bootstrap.rs

What it does on first run:
- Generates an Ed25519 key pair locally on device.
- Signs the temporary nickname with Ed25519.
- Prepares an X3DH-ready pre-key bundle using libsignal-client (Signal protocol primitives).
- Serializes secret material and passes only encrypted bytes to the storage layer.

Security constraints in module design:
- The module never writes plaintext key material to disk.
- Persistence is abstracted via EncryptedDeviceMaterialStore and accepts ciphertext only.
- Sensitive envelopes are zeroized from memory after use.

Public entrypoint:

```rust
bootstrap_or_load(temp_nickname, store, protector)
```

Required integration points from the app:
- EncryptedDeviceMaterialStore: your storage backend implementation (e.g. SQLCipher blob column).
- KeyMaterialProtector: your encryption/decryption policy (device-keystore backed key, etc.).
